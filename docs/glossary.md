# Glossary: LLM & Ollama Terms for Platform Engineers

Terms used across this lab, mapped to familiar Kubernetes, container, and distributed-systems concepts, with notes from what was actually measured on this machine (RTX 3080 10 GB, Ollama 0.40.2 → 0.40.13), covering Labs 01–06.

---

## 1. Packaging, Storage & Lifecycle

| Term | What it is | DevOps / Kubernetes Analogy | Observed in This Lab |
| :--- | :--- | :--- | :--- |
| **GGUF** | Binary file format (`llama.cpp`) containing quantized model weights, vocabulary, and metadata (`model.gguf`). | Read-only base container image layer | Mapped from disk into VRAM at load time (`mmap` / file read). |
| **Manifest** | JSON file under `~/.ollama/models/manifests/` listing the SHA-256 digests and media types of a model tag's layers. | OCI image manifest | Pulled models use `manifests\registry.ollama.ai\...`; locally built models (`ollama create`) use `manifests-v2\ollama.com\...` (Lab 01). |
| **Blobs** | Content-addressed files under `~/.ollama/models/blobs/sha256-<digest>`. The filename is the SHA-256 hash of the file content. | Node container image layer cache | Shared across tags and custom variants; `devops-assistant` and `qwen3.5:4b-q8_0` reuse existing weight/projector blobs (Labs 01–02). |
| **`mmproj` (Vision Projector)** | Separate GGUF blob (`application/vnd.ollama.image.projector`, e.g., a CLIP vision encoder) that projects images into the LLM's token embedding space. | Sidecar container bundled in the same pod spec | Loaded into VRAM (≈640 MiB on `qwen3.5:4b`, ≈880 MiB on `9b`) even on text-only prompts (Labs 01–02). |
| **`Modelfile`** | Declarative recipe (`FROM`, `PARAMETER`, `SYSTEM`, `TEMPLATE`) used by `ollama create` to build a model variant. | `Dockerfile` / Kustomize overlay | Parameters are **inherited and merged** with the base model's params layer; costs ~1.5 KB on disk (Lab 01 Step 4). |
| **`ollama list` vs `ollama ps`** | `list` (`GET /api/tags`) shows models stored on disk; `ps` (`GET /api/ps`) shows models currently loaded in VRAM/RAM. | `crictl images` vs `kubectl get pods` | `ollama list` reports decimal GB; `ollama ps` `SIZE` underestimates actual `nvidia-smi` VRAM usage (Lab 01). |
| **`llama-server.exe`** | Child process spawned by `ollama.exe` on `127.0.0.1:<random-port>` to hold one loaded model and run inference. | Workload Pod managed by the node agent | Variants that share the same weights blob and load-time settings (`num_ctx`) share one `llama-server` runner (Labs 01–02). |
| **`keep_alive`** | Idle TTL (default `5m`) after which `ollama.exe` stops the `llama-server` process and frees VRAM. Reset on every request; `0` unloads immediately. | Serverless scale-to-zero window | Trading idle VRAM footprint against the ≈4–6 s cold-load latency (Labs 01, 04). |

## 2. Memory, Hardware & Performance

| Term | What it is | DevOps / Kubernetes Analogy | Observed in This Lab |
| :--- | :--- | :--- | :--- |
| **Quantization (`Q4_K_M`, `Q8_0`, `FP16`)** | Storing each weight in fewer bits (e.g., ~4.5–5 bits for `Q4_K_M`, 8 bits for `Q8_0`) with block scaling factors. | Lossy asset compression | Reduces VRAM and speeds up generation (fewer bytes read per token). On this GPU, more parameters at 4-bit (`9b Q4`) beat fewer parameters at 8-bit (`4b Q8`) for similar memory (Lab 02 Step 5b). |
| **Context Window (`num_ctx`)** | Maximum tokens (prompt + chat history + thinking + answer) a runner can hold at once. Default is `4096` in Ollama. | Fixed-size request/session ring buffer | Allocated upfront at model load time. Changing `num_ctx` forces a runner reload (≈4–6 s) (Lab 02 Step 3). |
| **KV Cache** | GPU memory storing Key and Value attention vectors for tokens in the active context so they aren't recomputed on every new token. | Per-session in-memory state cache | Scales with `2 × attention_layers × kv_heads × head_dim × num_ctx × bytes`. Identical (128 MiB at 4K, 2,048 MiB at 64K) for both `qwen3.5:4b` and `9b` (Lab 02). |
| **Hybrid Attention / Recurrent State** | Architecture (used by `qwen3.5`) where most layers keep a fixed-size recurrent state and only a subset of layers use full KV attention. | Fixed-size state buffer + smaller indexed log | Costs only **32 KiB/token** of KV cache (+50 MiB fixed recurrent buffer) vs 128 KiB/token for full-attention 8B models—and causes `llama-server` to disable KV context shifting (Labs 01–03). |
| **GPU Offloading (`num_gpu` / `-ngl`)** | Number of transformer layers placed in GPU VRAM vs system RAM. | Pod resource placement vs swapping to disk | Layers execute serially: offloading 27% of `qwen3.5:4b` layers to DDR4-2400 CPU RAM dropped generation speed by 81% (123 → 23.4 tok/s) (Lab 02 Step 4). |
| **Prompt Evaluation (Prefill)** | Processing all input prompt tokens in parallel before emitting the first output token (`prompt_eval_count / prompt_eval_duration`). | Compute-bound batch job | Fast on GPU (≈3,400–5,000 tok/s); degrades gently under partial offload, but drops to 76 tok/s on CPU-only (Lab 02). |
| **Autoregressive Generation (Decode)** | Generating output one token at a time (`eval_count / eval_duration`), reading all active model weights for each token. | Memory-bandwidth-bound sequential loop | Follows $\text{time/token} \approx 4.7\text{ ms} + \text{weights}_{\text{GPU}} \div 770\text{ GB/s}$ on the RTX 3080 (Lab 02). |
| **Time to First Token (TTFT)** | Client wait time from sending the request to receiving the first token chunk: `cold_load (if any) + prompt_eval + 1 token`. | Time to First Byte (TTFB) | Warm streaming TTFT is ≈0.06–0.10 s; cold start adds ≈4–6 s (or ≈40 s if the NVIDIA CUDA `ComputeCache` is cold) (Labs 02, 04). |
| **Prefix / Prompt Cache** | Reusing KV cache entries from the previous request in the same slot when the new prompt shares a common token prefix (`prompt_eval_cached_count`). | Warm connection / warm cache hit | Persists across requests while the runner stays loaded; saves compute time during multi-turn chat, but still consumes `num_ctx` space (Lab 03 Steps 2–3). For agents it's what makes a 16K-token prompt usable: ≈0.3 s to the first token on later turns (Lab 06 Step 5). |

## 3. Prompting, Context Management & Sampling

| Term | What it is | DevOps / Kubernetes Analogy | Observed in This Lab |
| :--- | :--- | :--- | :--- |
| **Chat Template / `RENDERER`** | Formatting a list of `{role, content}` messages into one flat token stream with special role markers (e.g., ChatML `<\|im_start\|>` / `<\|im_end\|>`). | Serializing structured config into a wire protocol | `qwen3.5` uses a built-in Go `RENDERER` and `PARSER` inside Ollama rather than a Modelfile Go template (Labs 01, 03). |
| **Thinking Mode (`think`)** | Emitting intermediate reasoning tokens inside `<think>...</think>` before the final response. | Running `terraform plan` before `apply` | Controlled via assistant-turn prefill (`<think>\n` vs `<think>\n\n</think>\n\n`). Counts toward `eval_count` and `num_predict`; fixes order-dependent reasoning errors (`sched-math`), but cannot invent missing facts (Lab 03 Steps 1, 3). |
| **System Prompt** | Instructions placed in the `system` role at the start of the token stream. | Application startup config (`ConfigMap`), **not** RBAC | Shapes vocabulary and format, and survives `/api/chat` overflow trimming—but is not a security boundary against contradictory user input (Lab 03 Steps 3b, 5b). |
| **Front Truncation vs Message Trimming** | How Ollama handles inputs exceeding `num_ctx` by default (`truncate: true`). | Silent ring-buffer drop (`kubectl logs --tail`) | `/api/generate` keeps `4 + (num_ctx - 4) / 2` tokens (cutting the front); `/api/chat` drops whole oldest messages while keeping `system`. Setting undocumented `truncate: false` fails fast with HTTP 400 (Lab 03 Step 5). The Anthropic endpoint (`/v1/messages`) cut like `/api/generate`: 16,137 → 2,050 tokens, losing Claude Code's question (Lab 06 Step 5). `/api/embed` keeps the *start* instead (Lab 05 Step 1). |
| **Context Shift** | Dropping older tokens from a full KV cache mid-generation so the model can keep generating past `num_ctx`. | Sliding window log rotation | Passed by Ollama (`--context-shift --keep 4`), but disabled by `llama-server` for `qwen3.5`'s hybrid architecture—generation stops when `prompt + eval == num_ctx` (Lab 03 Step 5a). |
| **Sampler Chain** | Pipeline that converts raw vocabulary scores (logits) into one chosen token: `penalties → top-k → top-p → min-p → temp → dist`. | Traffic filtering + weighted load balancing | Logged in `server.log`. Unknown option names (`bogus_option`) are silently ignored with a `WARN`; wrong option types (`temperature: "hot"`) return HTTP 500 (Labs 03–04). |
| **`temperature` & `seed`** | `temperature` scales probability sharpness (`0` = greedy top token); `seed` initializes the RNG for non-zero temperature draws. | Deterministic vs seeded-random test runs | `temperature: 0` (or fixed `seed` at `temperature > 0`) gave 100% identical outputs across 20 sequential runs on this GPU—including across `num_ctx` reloads (Lab 03 Step 2). |
| **Filters (`top_k`, `top_p`, `min_p`)** | Drop low-probability tokens *before* temperature scaling: fixed count (`top_k`), cumulative mass (`top_p`), or fraction of top token (`min_p`). | Health-score threshold for backend endpoints | Prevent high temperatures (`1.5`) from picking garbage tokens while preserving variety where the model is uncertain (Lab 03 Step 4b). |
| **Penalties (`presence`, `frequency`, `repeat`)** | Reduce scores of tokens already used in the output to discourage repetition loops. | Per-client rate limiting | Break word-for-word token loops, but do not stop idea-level looping when the model lacks a fact (Lab 03 Step 4a). |
| **Grounding** | Supplying the authoritative reference text directly in the prompt so the model extracts rather than recalls from weights. | Handing the on-call engineer the runbook | Turned 1/4 recall into 4/4 accuracy—and also proved that context overrides model memory even when the reference is poisoned (Lab 03 Step 6). |

## 4. APIs, Streaming & Integration

| Term | What it is | DevOps / Kubernetes Analogy | Observed in This Lab |
| :--- | :--- | :--- | :--- |
| **NDJSON Streaming (`stream: true`)** | Sending one newline-delimited JSON object per generated token chunk on `/api/*`, with `done: true` and timing metrics in the final line. | `kubectl logs -f` / chunked HTTP transfer | Cut warm perceived latency (TTFT) by ≈12× (`0.10 s` vs `1.18 s`) with zero throughput penalty (Lab 04 Step 1). |
| **`done_reason`** | Why generation stopped: `stop` (model emitted end-of-turn token) or `length` (hit a token limit). | Container exit code (`0` vs `OOMKilled` / timeout) | `length` means *either* `eval_count == num_predict` (output cap hit, e.g. thinking loop) *or* `prompt_eval_count + eval_count == num_ctx` (context window full) (Lab 03 Steps 1, 5). |
| **Structured Output (`format`)** | Passing `"json"` or a JSON Schema so the sampler masks out any token that would violate the grammar. | CRD OpenAPI schema validation | Guarantees syntactic validity (`35/35` valid vs `json-mode`'s `"null"` string), unless truncated by `length` (`0/35`). Does not guarantee factual content (Lab 04 Step 4). |
| **OpenAI Compatibility (`/v1/*`)** | Translation layer (`/v1/chat/completions`, SSE `text/event-stream`) allowing OpenAI SDKs and agents to call local Ollama models. | MinIO S3-compatible gateway | Strips native fields (`options`, `num_ctx`, `truncate`, `think`) without warning and omits timing durations. Because `qwen3.5` thinks by default, plain `/v1` calls think unless `reasoning_effort: "none"` is sent (Lab 04 Step 5). |
| **Single-Slot Queueing (`n_slots = 1`)** | Default `OLLAMA_NUM_PARALLEL=1` behavior where one model runner processes one request at a time and queues concurrent arrivals (up to `OLLAMA_MAX_QUEUE=512`). | Pod with `maxConcurrency: 1` behind a queue | Queue wait is hidden inside `total_duration`: $\text{Queue} = \text{total} - \text{load} - \text{prompt\_eval} - \text{eval}$. Alternating between two tags that share a weights blob but differ in `num_ctx` (`4b` vs `4b-ctx8k`) forces a runner reload on every switch (Lab 04 Step 6). |
| **Prompt Injection** | Untrusted data (logs, tickets, docs) containing instructions that hijack the model's output or tool calls. | SQL / command injection via untrusted input | User/log text bent command flags (Lab 03 Step 3b) and injected a fake `NoIncident` report that passed JSON schema validation (Lab 04 Step 4); through tool output it was followed 1/24 times by the 4b and blocked by the approval gate (Lab 06 Step 2). Requires deterministic source checks, approval gates, and least privilege. |

## 5. Embeddings & Retrieval (Lab 05)

| Term | What it is | DevOps / Kubernetes Analogy | Observed in This Lab |
| :--- | :--- | :--- | :--- |
| **Embedding** | A fixed-length vector (768 dims for `embeddinggemma:300m`, 1,024 for `qwen3-embedding:0.6b`) that places a text by meaning; compared with cosine similarity (vectors are unit length). | A fingerprint / content hash, but for meaning instead of bytes | Deterministic and batch-invariant (diff 0.0). Measures "about the same thing", not "means the same": "ready" vs "not ready" scored 0.83–0.89, above a real paraphrase (0.62–0.67). Scores are model-specific, so no universal threshold (Lab 05 Step 1). |
| **Embedding truncation** | `/api/embed` cuts inputs longer than the embedding model's context, from the **end**, with HTTP 200 (`truncate: false` → HTTP 400). | A log shipper that silently drops the tail of long lines | 19K chars → 2,048 / 4,095 tokens embedded; similarity to the start 0.98, to the end 0.83. A chunk whose fix is in its last paragraph gets indexed without it (Lab 05 Step 1). |
| **BM25** | Keyword ranking: term frequency × inverse document frequency, length-normalized. | `grep` with a relevance score | 10/10 on identifiers (`toomanyrequests`, exit codes), 5/10 on paraphrases (Lab 05 Step 2). |
| **Dense retrieval** | Ranking by embedding similarity between query and chunks. | Fuzzy match on meaning | 9–10/10 on paraphrases; weak on rare tokens: `toomanyrequests` ranked 8th (Lab 05 Step 2). |
| **Hybrid search + RRF** | Fusing a keyword and a dense ranking by Reciprocal Rank Fusion: each list adds `1/(k + rank)`, so no score calibration is needed. | Combining two health signals by rank instead of raw value | BM25 + qwen3: 33/33 on the author set, because the two fail on different questions. But on queries written by an agent (Lab 06 Step 4), RRF with `k = 60` preferred a runbook that was mediocre in both lists: right runbook first in only 6 of 14 searches. |
| **Chunking** | Splitting documents into retrieval units: whole document, Markdown sections, or fixed-size windows (± overlap). | Choosing the shard key | Structure beats word counts: fixed 60-word windows left 12 sections with no chunk of their own; the right *section* came first in only 33–35 of 51 questions even when the right document did (Lab 05 Step 3). |
| **Search small, return big (parent-document retrieval)** | Search small chunks for precision, put the whole parent document in the prompt for context. | Index on a narrow key, fetch the full row | Parents 47/51 vs chunks 44/51 cited correctly, for ≈0.1 s more per answer (Lab 05 Step 4). |
| **Hit@k / MRR** | Retrieval metrics: is the right item in the top *k*; mean of 1/rank of the first right item. | SLO on "found in the first page of results" | Hit@3 at the ceiling (32–33/33) made models impossible to rank; questions written without the runbook's words dropped BM25 from 82% to 56% (Lab 05 Steps 2–3). |
| **Author bias / eval distribution** | An eval set reflects how its questions were written. | Load-testing with the wrong traffic mix | Author questions leaked the runbooks' vocabulary; the agent's own queries in Lab 06 were keyword strings with names the runbooks don't contain. Measure with the queries your real users (or agents) send. |
| **RAG (Retrieval-Augmented Generation)** | Retrieve relevant documents, put them in the prompt, ask the model to answer from them with citations. | Handing the on-call engineer the runbook before the page | One example id in the prompt (`[oomkilled]`) became the most cited runbook; removing it raised correct citations by 7–14 answers. A 2× bigger reader (`9b`) did not score better (Lab 05 Step 4). |
| **Vector store (sqlite-vec)** | A database for vectors plus metadata; here one SQLite file with exhaustive (brute-force) search. | An embedded datastore, like SQLite for app state | Same rankings as numpy to 1e-6; metadata filters fixed the wrong-section problem (2/6 → 5/6); bit-quantized search + float32 re-rank lost nothing; 91 ms per query at 50,000 vectors (Lab 05 Step 5). |

## 6. Tools, MCP & Agents (Lab 06)

| Term | What it is | DevOps / Kubernetes Analogy | Observed in This Lab |
| :--- | :--- | :--- | :--- |
| **Tool calling loop** | The model returns `tool_calls` (name + JSON arguments) instead of text; the runtime executes them and sends results back as `role: "tool"` messages until the model answers. | An RPC client whose caller is a model | 0 invalid calls for `qwen3.5:4b`; every failure was judgment: stopping after one tool, reading current instead of previous logs (Lab 06 Step 1). |
| **Schema validation vs judgment** | Schemas check the *shape* of a call, not whether it's the right call or a real target. | Admission webhook validating a manifest | Invented pod names and `<crashing-pod-name>` placeholders passed every type check; one approver approved 6 such deletes (Steps 2–3). |
| **Approval gate (human in the loop)** | Code in the runtime that asks a human before any mutating tool runs. | A change-approval step in a pipeline | Denied every injected delete regardless of model. The model's *report* of a denial was unreliable ("would you like me to proceed?") (Steps 2, 4). |
| **Indirect prompt injection** | Instructions planted in data the agent reads (logs, docs, web pages). | Command injection through untrusted input | Followed 1/24 (4b) and 3/12 (9b, thinking off), 0/24 with thinking on; the gate stopped every attempt (Steps 2–3). |
| **Text tool calls** | A model with the `tools` capability that writes calls as plain JSON text, without the template's tags, so the runtime never executes them. | A service that declares a health port but never listens on it | `qwen2.5-coder:7b`: 3/24 without a parser, 19/24 with one, at the price of placeholder arguments (Step 3). |
| **MCP (Model Context Protocol)** | A JSON-RPC protocol for tool servers (stdio or HTTP): the host discovers tools at runtime (`tools/list`) and calls them (`tools/call`). Protocol `2026-07-28` is stateless per request; older revisions use an `initialize` handshake. | CSI: one interface, many drivers | ≈3 ms per call over stdio; the real costs are server start-up (≈2 s) and first-use work (≈0.9 s index build) (Step 4). |
| **Tool annotations** | `readOnlyHint`, `destructiveHint`, … sent by an MCP server about its own tools. *Hints*, not policy. | A label a pod sets on itself | A lying server + a host trusting the hints: 3/3 deletes ran with no approval; the host's own allowlist: 0/6 (Step 4). |
| **Anthropic Messages API (`/v1/messages`)** | Ollama's Anthropic-compatible endpoint, used by Claude Code via `ollama launch claude`. Usage: `input_tokens` = new tokens, `cache_read_input_tokens` = reused prefix. | Protocol adapter / API gateway | Over-long prompts are cut like `/api/generate` (first 4 + last half), not by dropping old messages: 16,137 tokens → 2,050 at 4K, and the question was lost (Step 5). |
| **OpenAI Responses API (`/v1/responses`)** | The endpoint Codex uses. Usage: `input_tokens` = the *whole* prompt, `input_tokens_details.cached_tokens` = the reused part. | Same adapter, different accounting | Hosted tools run *in Ollama*: `web_search` goes to ollama.com (401 without sign-in) (Step 6). |
| **Agent overhead** | The fixed prompt a production agent sends before your question: system prompt + tool definitions. | Sidecar overhead per pod | Claude Code: 16–19K tokens, 22–25 tools. Codex with ChatGPT apps: 53K tokens, 26 tools; with apps, plugins and MCP off: 1.7K tokens, 5 tools (Steps 5–6). |
| **Prefix cache for agents** | Ollama reusing the cached prompt prefix across turns, since an agent re-sends the whole conversation each turn. | Warm cache for a request that repeats its headers | First turn 3–8 s to the first token, later turns ≈0.3–1 s; hybrid models need 50 MiB recurrent-state checkpoints to resume (Step 5). |
| **Permission mode / stored trust** | How an agent decides what may run without asking: default (ask), auto (a classifier decides), workspace-write; plus decisions saved to config. | RBAC defaults and a cached `kubectl` context | Claude Code's auto-mode classifier ran on the local 4b and allowed every command; a Codex trust decision from one session removed every prompt in the next (Steps 5–6). |
| **Sandbox (fail closed)** | OS-level isolation for agent commands (Codex: restricted-token Windows sandbox). If it can't be set up, commands are refused, not run unprotected. | Pod Security admission rejecting the pod | Refused every command when a file was locked or a helper binary was missing; "read-only" still meant read access across the user profile (Step 6). |
| **Context window blind spot** | The agent's assumed context size vs the model's real `num_ctx`. | A client with the wrong `max_body_size` | Claude Code assumed 200K, Codex 249K, Ollama ran 64K (or 4K by default). Overflow is silent (Steps 5–6). |
